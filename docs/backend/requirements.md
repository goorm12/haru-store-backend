# 하루상점 — 백엔드 요구사항

- 작성일: 2026-10-20 / v0.1
- 대상 저장소: `haru-store-backend`
- 기준 문서·적용 상태: [문서 안내](../README.md)

## 1. 서버 범위

구매자 웹·Capacitor 앱과 판매자·플랫폼 관리자 반응형 웹에 하나의 회원 시스템과 거래 API를 제공한다. MVP 거래는 현장 결제+픽업이다. 공구는 상점 하나에 속하고 판매자는 여러 상점을 운영할 수 있다. 상점 간 상품·수량·예약 명단을 공유하지 않는다.

서버는 요청 인증, 대상 소유권, 거래 정책, 시간 경계, 수량·금액, 상태 전이, 입력 검증의 최종 판단을 수행한다. 클라이언트가 전송한 역할·회원 ID·금액·예약 가능 여부를 권한이나 확정 값으로 신뢰하지 않는다.

온라인 결제 승인·환불·정산·배송, 장바구니·쿠폰·리뷰·상품 옵션, 직원 초대, 최소 모집 인원 조건은 MVP 범위에 넣지 않는다. 현장 결제 기록과 실제 금융 거래는 구분한다.

## 2. 호출자와 접근 범위

| 호출자 | 허용 범위 | 필수 검증 |
| --- | --- | --- |
| 비회원 | 공개 상점·공구·공지 조회 | 공개·삭제·숨김·상점 제한 상태 |
| 구매자 | 본인 프로필·저장 상점·예약·알림·문의·신고 접수 | 세션 회원과 예약·문의 작성자 일치 |
| 판매자 | 소유 상점, 해당 상점 공구·예약·공지·문의, 준비 수량 | 판매자 역할 및 상점 소유권, 하위 대상 소속 |
| 플랫폼 관리자 | 신고 검토, 상품 숨김·상점 제한·해제, 거래 요청 처리 | 별도 관리자 권한, 조치 사유·이력 |

- 같은 카카오 계정은 같은 회원으로 연결한다. 최초 상점 개설 성공 시 판매자 역할을 부여하며 사전 승인은 없다.
- 한 계정이 구매자·판매자 역할을 함께 가질 수 있다. 관리자 권한은 가입·상점 개설로 획득할 수 없다.
- 상점 전환은 조회 범위 선택이다. 요청의 storeId와 listingId·reservationId의 실제 상점 관계를 함께 검사한다.
- 비공개 문의는 작성자와 해당 상점 판매자만 조회한다. 관리자라는 이유로 전체 문의 본문을 열람하거나 대신 답변하지 않는다.
- 구매자는 본인 댓글·메시지, 판매자는 본인 공지·답글·답변만 수정·삭제한다. 판매자에게 구매자 댓글 임의 수정·삭제 권한을 추가하지 않는다.

## 4. 정합성 요구사항

- 총 점유 수량은 예약 확정·픽업 완료·미수령 수량의 합이다. 취소만 반환하며 수량 감소 시 차이만 반환한다.
- 같은 구매자·공구에 유효 예약은 하나다. 취소 후 조건 내 재예약은 허용하고 픽업 완료 후 같은 공구 재구매는 금지한다.
- 예약 단가·예약자·취소 정책·픽업 약속은 스냅샷으로 보존한다. 이후 공구 변경을 기존 예약에 소급하지 않는다.
- 시간 기준은 Asia/Seoul과 서버 시각이다. 전날 23:59:59까지와 당일 00:00을 구분한다.
- 동시 예약·수정에도 수량 초과, 중복 유효 예약, 중복 수량 반환이 없어야 한다.
- 동일 요청 재시도로 예약·취소·게시물·알림 이벤트를 중복 생성하지 않는다.
- 예약 상태와 결제 기록 상태는 별도로 저장한다. 날짜 경과는 자동 미수령·취소가 아니다.

## 5. 개인정보·운영

연락처는 직접 입력 및 형식 검증이며 소유 인증 완료로 표시하지 않는다. 개인정보 응답과 로그는 업무에 필요한 범위로 제한한다. 토큰·카카오 인증 정보·문의 본문·연락처를 일반 로그나 잠금화면 알림에 넣지 않는다.

탈퇴 시 계정 접근 종료와 거래 보존을 분리한다. 미완료 거래로 요청을 무기한 거절하거나 모든 정보를 일괄 장기 보관하지 않는다. 보존 의무 주체·대상 필드·기간·기산일은 공통 정책의 출시 전 검토 항목으로 관리하고, 실제 보관·파기는 그 결정에 따라 구현한다.

세부 구현 방식은 이후 설계 단계에서 정한다. 현재 문서는 서버가 제공해야 하는 기능과 사업 규칙을 정의한다.
